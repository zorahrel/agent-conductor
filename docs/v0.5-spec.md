# v0.5 Spec — Headless daemon + MCP surface + time-series metrics

**Status**: Draft (2026-05-12)
**Branch**: `agent-vs-tessera-comparison`
**Author**: zorahrel
**Discussed against**: [`horang-labs/tessera`](https://github.com/horang-labs/tessera) v0.1.5 (host/controller architecture)

---

## 1. Why this release exists

`agent-conductor` v0.4 nailed the side-car / observer model: discover via `ps`, tail JSONL, derive status with deterministic rules, inject via `tmux send-keys`, audit append-only. It works.

But "primitives as a Node library" is a ceiling. Three painful gaps stop us from being useful outside the Node ecosystem:

1. **Non-Node clients can't consume the snapshot.** A Swift menu-bar app, a Rust TUI, an Electron dashboard, or — relevantly — `horang-labs/tessera` itself cannot `import { buildSnapshot }`. They re-implement.
2. **Host-mode workspaces don't see sessions they didn't spawn.** Tessera owns its `ChildProcess` agents but is blind to a Claude Code the human launched in tmux three hours ago. There is no protocol bridge.
3. **No historical view.** Every consumer re-parses JSONL to graph "how active was session X over the last 8 hours". That is wasteful and slow.

v0.5 ships three things, in priority order:

1. **MCP server** that exposes the existing library as MCP tools.
2. **Headless daemon** with HTTP + WebSocket transport for non-MCP consumers.
3. **Time-series metrics store** (local SQLite) so historical queries are cheap.

This release explicitly **does not** chase Tessera on UI, host-mode CLI ownership, Codex / OpenCode protocol parsers, or Electron packaging. Those are losing battles on their terrain.

## 2. Goals & non-goals

### Goals

- **G1**: A `agent-conductor mcp` subcommand starts an MCP server (stdio transport) advertising tools `snapshot`, `sessions`, `transcript`, `todos.list`, `todos.add`, `todos.complete`, `inject`, `audit.tail`.
- **G2**: A `agent-conductor serve` subcommand starts a long-running HTTP + WebSocket daemon. Default bind `127.0.0.1:port-or-pick`. JSON over HTTP for snapshot/read endpoints. WS event stream for `sessions:update`, `todos:update`, `audit:update`.
- **G3**: Both transports share a single in-process **`Observatory`** singleton (pollers, caches, registries). Starting both transports in the same process is fine.
- **G4**: A SQLite-backed time-series store at `$AGENT_CONDUCTOR_STATE_DIR/timeseries.db` (default `~/.local/share/agent-conductor/`). Schema: `samples(ts, provider, pid, refinedStatus, turnCount, toolCount, lastWriteAge)`. Configurable retention.
- **G5**: A Prometheus-format exporter on `/metrics`. Default off, opt-in via flag or env.
- **G6**: All write operations (`inject`, `todos.add`, `todos.complete`) still go through the existing audit log. **No regression on auditability** when called via MCP or HTTP.
- **G7**: When the daemon receives an `inject` request, the cwd-collision lock still applies. **No regression on safety.**

### Non-goals

- **NG1**: We do not become a workspace UI. No web frontend, no Electron, no Kanban.
- **NG2**: We do not own / spawn CLI processes. Host mode is Tessera's job.
- **NG3**: We do not parse Codex `app-server` JSON-RPC or OpenCode ACP. Side-car reads disk artifacts only.
- **NG4**: We do not implement multi-machine federation in v0.5 (kept in "maybe-someday").
- **NG5**: We do not add runtime deps. MCP transport via stdio JSON-RPC is implementable in <200 LOC without `@modelcontextprotocol/sdk` if it adds deps. (Re-evaluate: pulling the official SDK as a single small dep is acceptable — see Decision §6.)

## 3. Acceptance criteria

Each AC is independently testable and ships with at least one automated test.

### AC1 — MCP server stdio handshake

**Given** the binary `agent-conductor` is installed
**When** I run `agent-conductor mcp` and pipe a valid `initialize` JSON-RPC request on stdin
**Then** the process responds with `{"jsonrpc":"2.0","result":{"protocolVersion":"2024-11-05","capabilities":{"tools":{}},"serverInfo":{"name":"agent-conductor","version":"0.5.x"}}}` within 200 ms.

**Test**: `tests/mcp-stdio.bats.sh`. Spawns the binary, writes the handshake, asserts the response shape.

### AC2 — MCP `tools/list` returns canonical set

**When** a client sends `{"method":"tools/list"}`
**Then** the response includes exactly these tool names:

| Tool name | Read/Write | Maps to |
|---|---|---|
| `snapshot` | R | `buildSnapshot()` over `discover()` |
| `sessions` | R | `discover()` only |
| `transcript` | R | `readJsonlTailLines()` for a given path |
| `todos_list` | R | `listTodos()` |
| `todos_add` | W | `addTodo()` |
| `todos_complete` | W | `completeTodo()` |
| `inject` | W | `sendKeys()` + `appendAudit()` (cwd-lock enforced) |
| `audit_tail` | R | `tail` of `audit.jsonl` |

**Test**: `src/mcp/server.spec.ts` — spin server, list tools, assert names + input schema match a JSON snapshot.

### AC3 — MCP `tools/call` honors the same exit-code contract as the CLI

**When** a client calls `inject` with `{pid: <busy_pid_in_other_repo>, text: "y"}`
**Then** the response is `{isError: true, content: [...]}` with a structured error indicating `precondition: cwd_collision` — matching the CLI's exit code 3 semantics.

**Test**: `src/mcp/server.spec.ts` with a fake tmux + lock fixture.

### AC4 — HTTP daemon `GET /snapshot`

**Given** the daemon is running on `127.0.0.1:32140`
**When** `curl http://127.0.0.1:32140/snapshot`
**Then** response is `200 OK` with `Content-Type: application/json` and body matches the `OrchestratorSnapshot` type exported from the library.

**Test**: `tests/http.bats.sh`. Curls the live server, validates against TS type via `ajv` JSON-schema generated at build time.

### AC5 — WebSocket event stream

**Given** the daemon is running
**When** I connect a WS client to `ws://127.0.0.1:32140/events`
**Then** within 5 s of a Reminders todo being added, the client receives a frame `{"type":"todo:added","payload":{...}}`.
**And** within 5 s of a session entering `awaiting_user_input`, the client receives `{"type":"sessions:update","payload":{pid, refinedStatus:"awaiting_user_input"}}`.

**Test**: `tests/ws.bats.sh`. Uses `wscat` from devDependencies-only path or a tiny Node test client.

### AC6 — Time-series append on poll

**Given** the daemon is running with timeseries enabled (`--timeseries` flag or `AGENT_CONDUCTOR_TIMESERIES=1`)
**When** 60 s elapses with 2 sessions present
**Then** `samples` table has at least 4 rows (2 sessions × at least 2 poll cycles assuming 20 s poll interval).

**Test**: `src/timeseries/store.spec.ts`. Uses an in-memory SQLite + fake clock.

### AC7 — `GET /metrics` Prometheus format

**Given** daemon running with `--prometheus` flag
**When** `curl http://127.0.0.1:32140/metrics`
**Then** response is `200 OK` with `Content-Type: text/plain; version=0.0.4` and body parses as valid Prometheus exposition format. Includes:
- `agent_conductor_sessions_total{provider, status}` gauge
- `agent_conductor_inject_total{result}` counter
- `agent_conductor_todos_total{state}` gauge
- `agent_conductor_audit_bytes_total` counter

**Test**: `src/timeseries/prometheus.spec.ts` — assert exposition format with a small parser fixture.

### AC8 — Daemon graceful shutdown

**When** the daemon receives `SIGTERM`
**Then** within 2 s: pollers stop, WS clients receive `close` frame with code 1001, HTTP server stops accepting connections but drains in-flight requests, SQLite is checkpointed and closed, exit code 0.

**Test**: `tests/shutdown.bats.sh`.

### AC9 — Documentation: Tessera composition example

`docs/compose-with-tessera.md` walks through:
1. Start `agent-conductor serve` as launchd service
2. Configure Tessera (or any host-mode workspace) to read `GET /snapshot` for side-car sessions it doesn't own
3. Subscribe to WS events for live updates

**Test**: link-check + manual review.

### AC10 — Backward compat

Every public export from v0.4 is still exported and behaves identically. `npm test` from v0.4 callers' test suites passes against v0.5 (validated via a smoke test in `examples/`).

## 4. Out of scope (explicitly)

- **No CLI process spawning.** If you want `agent-conductor` to start a Claude Code for you, use Tessera. We're the side-car.
- **No protocol-level parsers for Codex / OpenCode.** They don't write disk transcripts the same way; their side-car story needs separate research (v0.6+).
- **No GUI.** None. Not even a status page. `/metrics` is the closest thing.
- **No remote mode.** Daemon binds `127.0.0.1` only, no auth layer, no TLS. v0.5 is single-machine. Remote story is v0.7+ and needs proper threat modeling.
- **No web UI for audit log.** `curl /audit/tail` returns JSON; humans can pipe through `jq`.

### Dependency policy

v0.4 has **zero** runtime dependencies. v0.5 may add **at most**:

- `@modelcontextprotocol/sdk` — if and only if a 200-LOC stdio handshake is unmaintainable. Re-evaluate during spike.
- A small HTTP server — prefer `node:http` + hand-rolled routing (the repo already does it for tmux/CLI). No Express / Fastify / Hono.
- A WebSocket server — prefer `ws` (smallest, battle-tested) if `node:http` upgrade handling proves painful. Add as runtime dep with reluctance.
- `better-sqlite3` for the timeseries store. Sync API, very small, zero deps of its own.

Total runtime deps target: **≤ 3**. Every addition needs a one-paragraph justification in the PR.

## 6. Decisions to make during the spike (Mossa #2)

These should resolve when implementing the MCP server, **before** the HTTP daemon work starts:

| # | Decision | Default | Re-evaluate if |
|---|---|---|---|
| D1 | Use `@modelcontextprotocol/sdk` or hand-roll JSON-RPC stdio | Hand-roll | SDK's dep tree is empty + handshake is ≤ 50 LOC |
| D2 | Tool naming: `snake_case` or `camelCase` | `snake_case` (matches Claude Code tool conventions) | MCP ecosystem standardises on camelCase |
| D3 | Should `inject` via MCP require an `approve` flag in the input? | Yes — `{pid, text, approve: true}` required, else error. Mirrors auto-pilot gate. | Users find it annoying in scripted workflows |
| D4 | Should `audit_tail` redact the `text` field for sessions with no caller identity? | No — local single-user is the threat model | Multi-user mode is added |
| D5 | Default poll interval for sessions | 5 s (matches current refinedStatus cache TTL × 2.5) | Battery-draining on laptops; consider 10 s |

## 7. Migration / compatibility

- v0.4 → v0.5 is **additive only**. No breaking changes to existing library exports, CLI flags, or audit log format.
- `agent-conductor mcp` and `agent-conductor serve` are new subcommands; existing `snapshot` / `sessions` / `inject` / etc. keep their exact behavior.
- New environment variables (`AGENT_CONDUCTOR_STATE_DIR`, `AGENT_CONDUCTOR_TIMESERIES`, `AGENT_CONDUCTOR_DAEMON_PORT`) all have defaults that preserve current behavior when unset.

## 8. Risks

| Risk | Severity | Mitigation |
|---|---|---|
| `@modelcontextprotocol/sdk` adds heavy dep tree | Medium | Hand-roll first; add SDK only if maintenance pain proves real |
| HTTP daemon becomes attractive nuisance for remote-mode requests | High | Bind `127.0.0.1` only, return 403 on `Host:` header that isn't loopback, document explicitly that remote needs a reverse proxy with auth |
| `better-sqlite3` native module install fails on user machines | Medium | Make timeseries opt-in; fall back to no-op store; document install steps |
| WS event stream becomes the "main API" and consumers stop using snapshot polling | Low | Document `/snapshot` as canonical state; WS is delta-only |
| Tessera adds its own side-car observability and we become redundant | Medium | Ship MCP first → become *consumable* by Tessera. Open a PR to Tessera's repo with the integration example. |
| AC1–AC10 are too granular, slow down implementation | Low | Spike (mossa #2) can prove out MCP independently before HTTP/timeseries; defer ACs that block on it |

## 11. Open questions

1. Should the MCP server be packaged separately (e.g. `@agent-conductor/mcp` on npm) so it's installable in isolation by users who want only the MCP surface? **Tentative**: keep it in the main package for v0.5; consider splitting at v1.0.
2. Should we expose a `subscribe` MCP tool that streams events? MCP doesn't have first-class WS — would need to be implemented via long-poll or stay HTTP-only. **Tentative**: HTTP/WS for streaming, MCP for request/response only.
3. Do we ship a `--config <path>` flag for the daemon (YAML/TOML)? **Tentative**: env vars only in v0.5; config file in v0.6 if users request it.
